# 2026-08-16 に見つけた、本番に関わる別件

/asobi を既存の検索基盤に載せ直す作業の途中で見つかった、**本番のトップページに
関わる問題**をここに残す。いずれも今回の依頼の範囲外なので**直していない**。
直すかどうか、いつ直すかはウエマツさんが決める。

作業中に見つけただけで、意図して調べたわけではない。**同じ種類の問題が他にも
あるかどうかは調べていない。**

---

## 1. Travelpayoutsに空港コードを渡している（価格の取りこぼし・収益に影響）

**何が起きているか**

Travelpayouts のデータAPIは**都市コード**でやりとりする仕様である。公式ドキュメントは
`origin` / `destination` を「出発都市／目的都市のIATAコード」と定義し、例として `MOW`
（モスクワ。空港は SVO / DME / VKO）を挙げている。応答も都市コードで返る。

既存の `src/lib/flight-sources/travelpayouts-provider.ts` は、`query.origin` /
`query.destination` をそのまま渡している。ここに入るのは既存の解決が返す**空港コード**
（東京→HND、ソウル→ICN、ミラノ→MXP）である。

**影響**

Travelpayouts が価格を返さない区間が出る。トップページは4社を統合しているため
画面上は空にならず、**他社の価格で埋まって見えなくなる**。つまり
「Travelpayoutsの最安値だけが欠けた状態」で比較されている可能性がある。

Travelpayoutsはアフィリエイトの取引先でもあるため、**表示される価格の精度と
収益の両方に関わる**。

**確からしさ**

/asobi 側では実測で確認済み（東京→ソウル・東京→ミラノが空、東京→セブだけ成功。
セブは空港コードと都市コードが同じ）。**既存の検索側では未実測。**
同じコードの渡し方をしている、という事実からの推測である。

**直すとしたら**

`src/lib/city-codes.ts`（今回追加）の `cityCodeOf()` を、プロバイダが
リクエストを組み立てる直前に1回かけるだけで済む。応答側も、要求したコードで
引くのではなく返ってきたキーをそのまま使う形（既存プロバイダはすでにこの形）。

## 2. 地名が別の空港に解決されている（4件）

既存の解決 `resolveCity()` に294件の地名を通した実測（2026-08-16）で、
次の4件が**別の場所**に解決された。あいまい検索（音の近さで拾う最終段）が
拾い違えている。

| 入力 | 解決結果 | 本来 |
|---|---|---|
| キリマンジャロ | **LIM**（リマ・ペルー） | JRO |
| バングラデシュ | **ZYL**（シレット） | DAC（ダッカ） |
| イラン | **ZAH**（ザヘダン） | IKA（テヘラン） |
| ルーマニア | **TGM**（トゥルグ・ムレシュ） | OTP（ブカレスト） |

キリマンジャロ→リマは大陸が違う。**本番のトップページでいま起きている。**

なお /asobi も今回から同じ解決を使うため、この4件は /asobi でも同じ結果になる。
直すと既存の検索の挙動が変わるため、今回の依頼の「既存の検索の挙動を変えない」
に従って触っていない。

## 3. 検索文に `YYYY-MM-DD` を書くと 500 で落ちる

**再現**：トップページの検索に「東京からソウルへ 2026-10-12」のように
ISO形式の日付を含む文を入れる。

**起きること**：`/api/parse-query` が HTTP 500 を返す。

```
RangeError: Invalid time value
  at parseDate (src/lib/parser.ts:295)
  at tryParseMultiCity (src/app/api/parse-query/route.ts)
```

`parser.ts` の「12/25」形式を扱う分岐が、ISO日付の一部（`10-12`）を月日として
拾い、`new Date()` に無効な値を渡している。

**実測の条件**：Anthropic の鍵が使えない状態（LLM解析が失敗して従来の解析へ落ちる経路）で
確認した。LLM解析が成功する本番では、この経路に入らない可能性がある。**本番では未実測。**

## 4. LLMが使えないときの予備の解析が、弱い解決しか使っていない

`toUnifiedLegacy()`（LLM解析が失敗したときの予備）は、地名の解決に
`resolveFromDB()` だけを使っている。`resolveCity()` の5段（英語DB→国名→日本語名→
AIRPORT_MAP→あいまい検索）を通らない。

そのため LLM が落ちている間は「ミラノ」が解決できず、行き先が空のまま検索される。
2026-08-16 の実測で確認（`東京からミラノへ` → 行き先が空文字）。

LLMが動いていれば起きないため、影響はLLM障害時に限られる。

## 5. プレビューとローカルの試験が、本番のキャッシュに書き込める

**これは推測ではない。2026-08-16 に実際に起こし、本番に約30分間、誤った
「便なし」が仕込まれた状態を作った。** 気づいたのは偶然である。

### 何が起きたか

`/asobi` の直行価格を4社統合に載せ替えた検証で、ローカルの開発サーバーから
`searchAllProviders()` を3回呼んだ。ローカルは4社すべての鍵が失効しているため
結果は0件だったが、**その「0件」が本番と共有のRedisにキャッシュとして
書き込まれた**（TTL 3時間）。

```
flight:v1:HND-MXP-2026-10-15:1:economy   flights=0件
flight:v1:KIX-CEB-2026-10-15:1:economy   flights=0件
flight:v1:KIX-MXP-2026-10-15:1:economy   flights=0件
```

この3時間のあいだ、本番 tobira-world.jp で**まったく同じ条件**
（同区間・2026-10-15・大人1名・エコノミー）を検索した人には
「便が見つかりません」と表示される。実際には便はある。

ウエマツさんの指示で、2026-08-16 05:16(UTC) に3件とも削除した。
削除前に0件であることを確認し、削除後に読み直して消えたことを確認している。
価格履歴（`pricehist:log:*` 18鍵）には触れていない。

### なぜ起きるのか

Redis の接続先 `KV_REST_API_URL` / `KV_REST_API_TOKEN` は Sensitive 指定では
ないため `vercel env pull` で手元に降りてくる。そして Production / Preview /
Development の3環境すべてで**同じ値**、つまり**同じRedis**を指している。

キャッシュの鍵（`flight:v1:...`）には環境を区別する印が無い。
そのため次の3つが同じ棚を共有している。

- 本番 tobira-world.jp
- プレビュー（各ブランチのデプロイ）
- 開発者の手元（`npm run dev`）

### なぜ気づきにくいか

- 書き込みは静かに成功する。エラーも警告も出ない
- 影響が出るのは「同じ区間・同じ日付・同じ人数・同じ座席クラス」を
  検索した人だけなので、再現しにくく、問い合わせも来ない
- 3時間で自然に消えるため、あとから調べても痕跡が残らない
- **鍵が失効している環境ほど「0件」を書きやすい。**
  つまり、いちばん壊れた環境が、いちばん有害なデータを本番に置く

### 影響の範囲（今回だけの話ではない）

キャッシュの書き込みは `searchAllProviders()` の中にあり、
`api/search` `api/search-multi` `api/cron/check-prices` `/asobi` の
どこから呼んでも起きる。今後もローカルやプレビューで検索を1回試すたびに、
本番の棚に結果が入る。**中身が正しければ無害だが、0件だと有害である。**

### 考えられる対処（今回は実施していない）

- キャッシュの鍵に環境名を入れる（`flight:v1:preview:...`）。
  `VERCEL_ENV` は各環境に自動で入っているので判定はできる
- 0件の結果をキャッシュしない、または0件だけTTLを極端に短くする。
  これは環境を問わず効く。「データが無い」と「取得に失敗した」を
  区別できていないのが根にあるため
- 手元の開発では本番Redisに繋がない（開発用の接続先を別に用意する）

どれを採るかは未定。対処は別途判断する。
